# AI Воркбенч (етапи 1–3c: каркас, контекст, агенти, пошук, захист даних)

Персональна PWA з агентами на Claude API. Етап 1: проксі з лімітом витрат на Vercel, встановлюваний застосунок (PWA), сховище Dexie, стрімінг відповіді, агент «Документи».
Етап 2: профіль, пам'ять, пошук BM25, збирач контексту з бюджетом токенів і панель контексту.
Етап 3a: цикл tool use, правки з diff і підтвердженням, реєстр агентів, шторка агентів і slash-команди.
Етап 3b: агенти «Перевірка» і «Пости» зі структурованим виходом.
Етап 3c: агент «Пошук» з веб-пошуком і цитатами, черга підтвердження пам'яті.

```
Браузер (PWA, IndexedDB) ──HTTPS──► /api/claude (Vercel Function) ──► api.anthropic.com
                                     токен · білий список моделей · ліміти витрат (Upstash Redis)
```

## Розгортання (достатньо телефона)

1. Створіть репозиторій на GitHub і залийте вміст архіву (разом із `package-lock.json`).
2. Vercel → **Add New → Project** → імпорт репозиторію. Framework визначиться як Vite.
3. У проєкті: **Storage → Marketplace → Upstash Redis** → підключіть до проєкту. Інтеграція сама додасть змінні `KV_REST_API_URL` і `KV_REST_API_TOKEN` (або `UPSTASH_REDIS_REST_*`). Підтримуються обидва варіанти.
4. **Settings → Environment Variables** (для Production і Preview): `ANTHROPIC_API_KEY`, `APP_TOKEN` (довгий випадковий рядок), `DAILY_LIMIT_USD`, `MONTHLY_LIMIT_USD`. Повний список у `.env.example`.
5. **Redeploy**, відкрийте адресу проєкту, введіть `APP_TOKEN`.
6. Safari → «Поділитися» → «На початковий екран». Застосунок запуститься як окремий PWA.

Без Redis або без `APP_TOKEN` проксі **відмовляє у всіх запитах** (так задумано: без лічильника витрат ліміт не працює).

## Моделі та ціни

Конкретні моделі згадуються лише в `src/core/settings.ts` (`MODEL_MAP`) і в таблиці цін `shared/pricing.ts`. Проксі приймає тільки моделі з цієї таблиці. Ціни взято з документації Anthropic станом на жовтень 2026 (Haiku 5.5: $0,10/$0,50, Sonnet 5.5: $2/$10, Opus 5.5: $4/$20 за 1 млн токенів). Звіряйте їх із [сторінкою цін](https://platform.claude.com/docs/en/about-claude/pricing); якщо змінилися, задайте `PRICES_JSON` у Vercel без перебирання коду. Ціна читання кешу Sonnet 5.5 у джерелах розходиться ($0,20 → $0,10 після зниження), у коді стоїть $0,10.

## Де зберігаються дані й перенесення

Дані лежать в IndexedDB браузера, окремо для кожної адреси й кожного способу входу. **На iPhone вкладка Safari й іконка на початковому екрані мають різні сховища**, а кожен деплой Vercel може мати власну адресу. Тому порожня «Пам'ять» найчастіше означає, що застосунок відкрито не звідти, де дані вводились. На екрані «Параметри» видно поточний режим і адресу. Перенести дані можна через «Експортувати базу» і «Імпортувати» (там же й в порожній «Пам'яті»). Імпорт лише додає: однакові факти й наявні записи пропускаються, профіль доповнюється заповненими полями. Файл `seed/workbench-seed.json` це готовий пакет для першого заповнення.

### Хмарна копія й діагностика

IndexedDB на iPhone ненадійна: її можуть очистити система чи браузер, у вкладки й іконки окремі сховища, у деплоїв різні адреси. Тому є **хмарна копія** профілю, фактів і артефактів у вашому Redis (журнал запусків не копіюється, ліміт копії 0,5 МБ). Вмикається в «Параметри → Хмарна копія»: ручне «Зберегти копію зараз» і автокопія за кілька секунд після змін.

- Порожній локальний стан **ніколи не відправляється**, а сервер відхиляє порожню копію й зберігає попередню (`backup:prev`), тож очищена база не затре справжню копію.
- Якщо локальна база порожня, а копія є, на екрані «Пам'ять» з'являється банер «Знайдено хмарну копію → Відновити». Відновлення лише додає, дублів немає.
- «Параметри → Стан сховища»: дата створення сховища, лічильники записів, **самоперевірка запису** (пише, читає назад, видаляє). Якщо localStorage пам'ятає попередній запуск, а IndexedDB порожня, показується попередження, що базу очищено окремо.
- Збереження профілю й фактів перевіряється читанням назад; помилка запису показується повідомленням, а не мовчки.
- Схема бази піднялась до v2 (додана службова таблиця `meta`); наявні дані не змінюються.

## Як працює контекст (етап 2)

Кожне джерело (профіль, закріплені факти, пам'ять, споріднені документи, фрагмент, історія) це рядок на екрані «Контекст» з перемикачем, токенами й переглядом того, що піде в запит.

| Рівень | Джерела | Як потрапляє в запит |
|---|---|---|
| Постійний | профіль, закріплені факти | у системний префікс, що кешується |
| Релевантний | пам'ять, документи за темою задачі | пошук BM25 по тексту задачі, топ-K |
| Оперативний | фрагмент, історія сесії | напряму |

Бюджет токенів залежить від рівня моделі (`CONTEXT_BUDGET`). Профіль і фрагмент **не скорочуються**; решту скорочують за пріоритетом: спершу відкидаються останні елементи (в історії найстарші), потім середина тексту, потім усе джерело. Про скорочення панель попереджає. Історія сесії вимкнена за замовчуванням (вмикається перемикачем).

Пошук українською працює без ембедингів: слова обрізаються до 6 літер (документи, документів, документами → «докуме»), плюс префіксний і нечіткий збіг. Для ваших обсягів (сотні записів) цього вистачає; ембединги додамо, коли записів стане понад 1–2 тисячі.

Пам'ять змінюється лише вами: факти додаються вручну або кнопкою «Запам'ятати» під відповіддю (з редагуванням і підтвердженням). Поля профілю можна позначити «приховано»: вони не потрапляють у запити.

## Агенти й інструменти (етап 3a)

`runAgent` виконує цикл tool use: модель викликає інструменти, застосунок виконує їх і повертає результат, доки модель не дасть відповідь без виклику. Запобіжник: не більше 12 кроків за запуск. Усі кроки одного запуску тарифікуються й підсумовуються в журналі (`steps`, `toolCalls`).

| Інструмент | Що робить | Підтвердження |
|---|---|---|
| `search_context` | шукає в пам'яті й бібліотеці (BM25) | ні |
| `read_artifact` | читає артефакт частинами (`offset`, `limit`) | ні |
| `apply_edits` | точкові правки {find, replace} або {insertAfter, text} у фрагменті чи артефакті | **так, diff** |
| `save_artifact` | створює новий артефакт (існуючі не перезаписує) | ні |
| `ask_user` | питання користувачу з варіантами | відповідь користувача |

`apply_edits` показує diff: кожну правку можна прийняти або зняти. Правка, чий фрагмент не знайдено або він неоднозначний, не застосовується, а модель отримує причину й може виправитись. Зміна артефакту створює нову версію (стара лишається, на екрані «Бібліотека» є відкат). Відхилення повертається моделі як помилка інструмента.

Агента вибирають тапом по заголовку на екрані «Робота» або командою на початку задачі (`/док`). Новий агент це маніфест у `src/agents/registry.ts`.

## «Перевірка» і «Пости» (етап 3b)

Обидва агенти повертають результат **викликом завершального інструмента** (`finalTool`). Для сумісності з актуальними моделями Claude запит використовує `tool_choice: { type: "auto" }`, а не примусові типи `tool`/`any`. `runAgent` перевіряє, чи модель викликала потрібний `finalTool`; якщо ні — додає інструкцію й повторює крок. Вхід інструмента перевіряється схемою, після успішного виклику запуск завершується.

**Перевірка** (`/перевір`). Режими пишуться в задачі: `language`, `facts`, `logic`, `style`, `code`, `brief` (без режимів: language, logic, style). Результат: вердикт, оцінка 0–10, зауваження з серйозністю, категорією, дослівною цитатою, проблемою й порадою. Якщо правка механічна, зауваження має `replacement`, і кнопка «Застосувати виправлення» перетворює такі зауваження на правки з diff (той самий `apply_edits` з підтвердженням). Цитати з `replacement` перевіряє код: якщо їх немає в тексті дослівно, модель отримує помилку й один раз виправляється. Вердикт обчислюється з серйозності (low не блокує).

**Пости** (`/пост linkedin: тема`). Платформа береться із задачі (за замовчуванням LinkedIn), за замовчуванням 3 варіанти. Правила платформ (ліміт символів, кількість хештегів, 210 символів до «ще» у LinkedIn) це дані в `src/agents/platforms.ts`. **Довжину й хештеги рахує код, а не модель**: якщо правила порушено, модель отримує помилку з цифрами й один раз виправляє, після другої спроби результат приймається з позначкою про перевищення. Збережені пости (кнопка «Зберегти») потрапляють у бібліотеку як `post` і стають зразками стилю для наступних запусків.

Кнопка «Перевірити» під відповіддю або варіантом поста передає текст у «Перевірку».

## «Пошук» і черга пам'яті (етап 3c)

**Пошук** (`/пошук питання`). Агент спершу дивиться у ваші нотатки (`search_context`, пам'ять, збережені звіти), потім шукає в інтернеті серверним інструментом Anthropic `web_search` (до 10 пошуків за запуск). Відповідь це Markdown із маркерами цитат `[1]`, `[2, 3]` і списком джерел під нею; джерела мають спільну нумерацію, однакові URL об'єднуються. Мітки в картці показують кожен пошуковий запит. Якщо сервер не встиг завершити пошук за один запит (`pause_turn`), застосунок сам продовжує, повертаючи відповідь без змін.

- **Вартість:** $10 за 1000 пошуків ($0,01 за один) плюс токени результатів. У підсумку під відповіддю видно кількість пошуків і вартість. Проксі перед запитом враховує найгірший випадок (токени + `max_uses` × $0,01) і відмовляє, якщо це перевищує денний чи місячний ліміт.
- **Захист на проксі:** з серверних інструментів дозволено лише `web_search_20250305`, і лише з `max_uses` від 1 до `MAX_WEB_SEARCHES` (за замовчуванням 10). Інші серверні інструменти (наприклад, виконання коду) відхиляються.
- **Налаштування пошуку:** `src/agents/search.ts` (кількість пошуків, локалізація `user_location`, за замовчуванням без прив'язки до країни; обмеження доменів `allowed_domains`/`blocked_domains`). Веб-пошук має бути увімкнений для вашої організації в Anthropic Console; якщо запит повертає помилку про недоступність, перевірте це.
- **Звіти:** кнопка «Зберегти» створює артефакт `search_report` («Пошук: тема») разом зі списком джерел. Збережені звіти потрапляють в інші запуски як `<untrusted_content>`: системні промпти всіх агентів велять сприймати такий вміст як дані, а не інструкції.

**Черга пам'яті.** Агенти «Документи» і «Пошук» мають інструмент `propose_memory`: факт потрапляє не в пам'ять, а в чергу «На підтвердження» (екран «Пам'ять», лічильник на вкладці). До 3 пропозицій за запуск; дублі з пам'яттю, чергою й відхиленими відсікаються (відхилене агент більше не пропонує). Пропозиції після веб-пошуку позначені «З веб-джерел: перевірте особливо уважно». Прийняти можна як є або відредагувавши.

## Ланцюги й рецепти (етап 4: T4.1 ядро, T4.2 інтерфейс)

`runChain` (`src/core/orchestrator.ts`) виконує кроки послідовно: вихід кроку стає `upstream` наступного, кожен агент збирає власний контекст, усі запуски мають спільний `chainId` у журналі. Рецепт це дані (`src/agents/recipes.ts`); перший: **«Пост з дослідженням»** (`/пост-з-пошуком linkedin: тема`): Пошук → Пости (3 варіанти) → Перевірка (`facts, language`, за потреби виправлення й повторна перевірка; на перевірку йде перший варіант поста, що вкладається в правила платформи, разом зі звітом пошуку).

- **Ліміт вартості діє на весь ланцюг** (за замовчуванням $0,25): перед кожним кроком до фактично витраченого додається найгірший випадок кроку (вхідні токени + повний `max_tokens` + усі дозволені пошуки). Це оцінка одного виклику моделі: токени результатів пошуку й додаткові кроки циклу не враховано, авторитетний облік і справжні ліміти лишаються на проксі. Якщо сума перевищує ліміт, ланцюг зупиняється (або питає підтвердження, коли інтерфейс його надає).
- **Цикл «Перевірка → виправлення».** Якщо «Перевірка» повертає `needs_changes`, «Пости» один раз переписують варіанти за зауваженнями (вони бачать звіт пошуку, попередні варіанти й зауваження за серйозністю), після чого «Перевірка» повторюється на виправленому тексті. Виправлення й повтор це звичайні кроки: рахуються в ліміт 6 кроків і в ліміт вартості (перед кожним можливе підтвердження). Кроки доопрацювання підписані «Крок 4 · Пости (виправлення)». Якщо після повтору вердикт усе ще `needs_changes`, він лишається видимим: далі правки робите ви. Механізм загальний (`ChainStep.retry`, до 2 повторів) і не прив'язаний до цього рецепта.
- Не більше 6 кроків; невідомий агент, порожній ланцюг і некоректний ліміт відхиляються до першого запиту.
- Точка зупинки (`pauseAfter`) і перевищення ліміту без обробника підтвердження зупиняють ланцюг (fail-closed).
- Якщо будь-який попередній крок читав інтернет, `upstream` наступних кроків обгортається в `<untrusted_content source="web-derived">`.
- **Інтерфейс (T4.2).** Рецепт запускається командою на екрані «Робота»: `/пост-з-пошуком X: тема` (слеш необов'язковий, на iPhone зручніше без нього: «Пост-з-пошуком X: тема»; або тап по заголовку екрана → «Рецепти» → вибрати рецепт, команда підставиться в поле; платформа `telegram`, `linkedin`, `x` або `facebook`; без неї LinkedIn). Зверху ланцюг показує кроки зі станами й витрати проти ліміту, нижче кожен крок це звичайна картка. Якщо оцінка кроку перевищує ліміт, шторка питає «Продовжити / Зупинити». «Зупинити» біля поля вводу перериває ланцюг. Фрагмент (скріпка) у ланцюгу не використовується. Ліміт змінюється в «Параметри → Ліміт одного ланцюга» (зберігається на пристрої).
- **Журнал (T4.2b).** У «Бібліотека → Журнал запусків» кроки ланцюга зібрані в один запис «Рецепт · тема» із сумою витрат; всередині кроки «Крок 2 з 3 · Пости». Вихід «Постів» і «Перевірки» показується читабельно, а не JSON. Запуск зберігає `chain` ({recipe, topic, index, total}); записи, зроблені до T4.2b, групуються за `chainId` із заголовком «Ланцюг · Пошук → Пости → Перевірка».
- **`handoff` (T4.4).** Агент сам передає частину задачі іншому агентові інструментом `handoff`: «Документи», «Перевірка» й «Пости» можуть передати завдання **лише «Пошуку»**, наприклад коли в тексті є твердження без джерела. Кожна передача показує шторку «Передача завдання» з інструкцією і оцінкою вартості (найгірший випадок); «Дозволити» запускає пошук, «Відмовити» повертає агенту відмову, і він продовжує без неї. Результат повертається агентові як недовірений вміст (джерела списком). Глибина вкладення до 2, не більше 2 передач за запуск, самопередача заборонена. Вкладений запуск не пишеться в журнал окремо: його вартість входить у батьківський запис, де видно рядок «Передача → Пошук».

## Роутер і режим «Авто» (етап 4, T4.3)

Тап по заголовку екрана «Робота» → **«Авто»**. Далі ви пишете задачу своїми словами («знайди, що нового про Web Push на iOS, і зроби пост для X»), а роутер (модель `fast`, один дешевий виклик, менше $0,001) складає **план** із наявних агентів і рецептів. План показується **завжди**, нічого не запускається, доки ви не натиснете «Запустити».

- **Що в плані.** Один агент, ланцюг із кількох кроків, готовий рецепт («Пост з дослідженням» з циклом виправлення) або уточнювальне питання, якщо задача неоднозначна. Картка показує підсумок, кроки з інструкціями, впевненість, оцінку вартості (сума найгіршого випадку кроків без проміжних результатів) і ліміт ланцюга. Нижче 0,6 є попередження й кнопка «Запустити все одно».
- **Виконання.** Один агент іде звичайним запуском (з вашим фрагментом). Кілька кроків або рецепт йдуть через `runChain` (ліміти кроків і вартості, шторка підтвердження, журнал «Авто · задача»). Фрагмент отримує лише перший крок.
- **Захист.** Відповідь `route_decision` перевіряє код: відомі агенти й рецепти, не більше 6 кроків, непорожні інструкції; `tool_choice: auto` і один повтор, якщо модель не викликала інструмент або план хибний. Задача йде в `<task>`; вміст фрагмента роутеру не передається, лише довжина.
- **Команди.** Явна команда (`/док …`, `/пост-з-пошуком …`) обходить роутер. Команда агента виводить із режиму «Авто»; рецепт лишає в ньому.
- **Витрати.** Виклик роутера не пишеться в журнал запусків, але враховується проксі. Вартість показано на картці плану.

## Пакет інженерних специфікацій і агент «Інженер» (етап 5: T5.1 модель, T5.2 агент)

Агент «Інженер» (SOFTWARE ENGINEER, етап 5) проєктуватиме програмні модулі до того, як агент «Код» почне їх реалізовувати. Перший крок це **модель пакета** (`src/engineering/package.ts`): мінімальний набір із чотирьох документів як структуровані дані. Тексти документів відтворюються з даних.

| Документ | Дані пакета |
|---|---|
| `REQUIREMENTS.md` | вимоги `REQ-001…` з пріоритетом, позначкою confirmed / preference / assumption і критеріями прийняття; відкриті питання `Q-001…` |
| `ARCHITECTURE.md` | опис архітектури й компоненти `COMP-001…` (відповідальність, вхід, вихід, залежності), діаграма Mermaid |
| `DATA_MODEL.json` | сутності `ENT-001…` з полями й зв'язками |
| `TASKS.json` | задачі `TASK-001…`: вимоги, компоненти, залежності, файли, критерії, спосіб перевірки, порядок виконання |

- **Перевірка кодом (`validatePackage`).** Унікальні id, усі посилання існують, немає циклів залежностей, кожна обов'язкова вимога покрита задачею, кожна задача має критерії й спосіб перевірки, припущення не видаються за вимоги. З `complete: true` ще й непорожні розділи та жодного невирішеного блокувального питання.
- **Життєвий цикл.** DRAFT → REVIEW → APPROVED → IN_IMPLEMENTATION → COMPLETED (також CHANGE_REQUESTED, ARCHIVED). У REVIEW і APPROVED пакет переходить лише після перевірки; **затвердити може лише користувач**. Зафіксована версія незмінна: зміни тільки ревізією (`revise`) з новим номером версії (1.0 → 1.1), попередня версія лишається як була.
- **Простежуваність.** `traceability`: вимога → компоненти → задачі → способи перевірки. `taskOrder` і `readyTasks` дають кодеру порядок і точку старту.
- **Сховище.** Пакет це артефакт типу `engineering_package` (запис `${packageId}@${version}`), тож експорт, імпорт і хмарна копія працюють без змін. Зафіксовану версію не можна перезаписати змістом.

### Агент «Інженер» (T5.2)

`/інженер` або тап по заголовку екрана «Робота» → «Інженер». Агент проєктує, а не пише код: за вашим описом і документами проєкту з бібліотеки він складає **чернетку пакета**.

- **Як наповнює.** Окремий інструмент на розділ: `create_package`, `set_requirements`, `set_architecture`, `set_data_model`, `set_tasks`, `set_open_questions`. Кожен виклик замінює свій розділ повністю; код перевіряє форму входу, а у відповіді повертає моделі проблеми всього пакета (невідомі посилання, цикли, непокриті вимоги), тож агент виправляє їх наступним викликом. Перед передачею на перегляд він викликає `check_package`, потім `request_review`.
- **Чого не може.** Затвердити пакет: такого інструмента немає, затверджує лише користувач. Змінювати пакет, що вже на перегляді чи затверджений (повертається помилка): нову версію створює користувач. Створювати другий активний пакет для того самого проєкту.
- **Контекст про існуючий проєкт.** Агент не бачить код напряму. Збережіть у «Бібліотеку» README, PLAN, CLAUDE та файли, які стосуються модуля (краще з позначкою версії в назві, наприклад «README @26639e4»), і додайте їх у «Контекст». Агент читає їх частинами (`search_context`, `read_artifact`) і бере структури, назви полів та команди звідти, а версії вказує в `summary` пакета.
- **Готовий набір документів.** `npx tsx scripts/make-context-bundle.ts out.json README.md PLAN.md src/db/importexport.ts …` збирає файл імпорту: кожен файл стає записом «Бібліотеки» з назвою «шлях @sha» (файл проходить перевірку схеми імпорту). Його імпортують у «Параметри → Імпортувати».
- **Дослідження.** За потреби зовнішнього факту агент передає його «Пошуку» (`handoff`, з вашим підтвердженням).
- **Вартість і довжина.** Модель `balanced`; ліміт кроків циклу 24 (проєктування займає 8–15 викликів). Кожен розділ це окремий невеликий запит, а не один величезний.
- **Де результат.** Пакет з'являється в «Бібліотеці» як артефакт `engineering_package` («Пакет: проєкт v1.0 · DRAFT»). Екран перегляду із затвердженням буде в T5.4.

## Сумісність із Claude API та потокові відповіді

Клієнт працює через власний fetch + SSE у `src/core/claude.ts`; серверний проксі `api/claude.ts` пересилає запит і потік Anthropic, перевіряє модель, ліміти токенів та бюджет.

Останні виправлення сумісності:

- Параметр `temperature` вилучено з запитів: для моделей, які його не підтримують або позначають застарілим, він спричиняв помилку.
- Для агентів зі структурованим виходом `tool_choice` переведено на `auto`: типи `tool` та `any` не підтримуються деякими актуальними моделями. Обов'язковість `finalTool` забезпечує клієнтська перевірка в `src/core/runner.ts` із повторним запитом, якщо модель не викликала потрібний інструмент.
- SSE-клієнт накопичує `thinking_delta` і `signature_delta` у відповідному content block. Це важливо, бо відповідь асистента з thinking-блоками може повертатися в наступному запиті як частина історії; блоки та їхні підписи не можна довільно відкидати або перетворювати на звичайний текст.
- Також зберігаються tool-use JSON-частини та цитати веб-пошуку. Історію повідомлень потрібно передавати в Anthropic у допустимій структурі content blocks.

**Статус:** виправлення внесені в код, але повний `npm run check` після останньої зміни та наскрізне тестування на iPhone ще не підтверджені. До цього не вважайте сумісність усіх моделей остаточно перевіреною.

Якщо з'являється помилка формату повідомлень або thinking-блоку:
1. Збережіть точний текст помилки й активну модель.
2. Не очищайте IndexedDB і не видаляйте історію запуску до діагностики.
3. Перевірте, чи помилка виникає на новій короткій сесії без попередніх повідомлень. Якщо лише в продовженні — перевіряти round-trip історії content blocks у `src/core/claude.ts` та `src/core/runner.ts`.
4. Запустіть `npm run check`; потім перевірте реальний сценарій на пристрої.
## Відомі обмеження

- Режим `facts` у «Перевірці» без веб-пошуку: твердження, яких не можна перевірити за контекстом, позначаються як сумнівні. Для перевірки фактів користуйтеся агентом «Пошук».
- Використано базову версію веб-пошуку (`web_search_20250305`). Версії з динамічною фільтрацією результатів (менше токенів, але виконання коду на боці Anthropic) не підключено.
- Черга пропозицій пам'яті не входить у хмарну копію й експорт: це тимчасові дані.
- Порожній вихід інструмента (модель не викликала `submit_*`) показується як звичайний текст.
- Кожен крок циклу повторно надсилає контекст: префікс кешується, але довгі цикли дорожчі за один виклик.
- Історія сесії живе в пам'яті сторінки й губиться при перезавантаженні.
- Мітка кешу діє, лише якщо префікс (інструкції + профіль + закріплені факти) перевищує мінімальний розмір кешу моделі (≈1024 токени). Для короткого профілю кешу не буде, це нормально.
- Запуск без мережі показує помилку, черги запитів ще немає (етап 7). Оболонка й бібліотека працюють офлайн.
- Вартість у застосунку це оцінка з `usage`; авторитетний лічильник тільки на проксі.
- Токен доступу лежить у `localStorage`; захист від викрадення скриптами дає суворий CSP (`vercel.json`).

## Відхилення від специфікації

- **Node.js замість Edge.** Vercel позначив Edge Functions застарілими; проксі це звичайна функція Node.js з Web Handler (`export function POST(request)`).
- **Власний fetch + SSE замість `@anthropic-ai/sdk`.** Для етапу 1 це менше коду і простіший шлях `/api/claude`. SDK підключимо на етапі 3 разом із tool use, якщо знадобиться `finalMessage()`.
- **`pinned` у пам'яті це `0 | 1`.** IndexedDB не індексує boolean, тому запит `where("pinned").equals(1)` зі специфікації з `boolean` не спрацював би.
- **Підпис вкладки «Параметри».** П'ять вкладок на 375 pt не вміщують слово «Налаштування» (назва екрана лишилась повною).
- **401 для невірного токена** (замість 403), щоб клієнт відрізняв «вийти» від інших помилок.
